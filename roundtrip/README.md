# Round trip: edit the deck in PowerPoint, get the edits back into the code

The viewer in the repository root only shows slides. These scripts close the loop for a deck that is
generated by code (pptxgenjs): a save from PowerPoint flows back into the generator, and a change in the
generator flows into the `.pptx` the viewer shows. Nothing is overwritten without a backup.

```
deck.mjs / theme.mjs / overrides.json  ──node deck.mjs──▶  out/deck.pptx + out/manifest.json
            ▲                                                      │
            └────────── tools/sync-back.mjs ◀── save in PowerPoint ─┘
```

## Install into a deck project

Copy this directory into the deck project as `tools/` (or symlink it) and start the viewer with the
`.pptx` among the watched files:

```bash
cp -r /path/to/pptx_live_preview/roundtrip  tools
chmod +x tools/*.sh tools/*.mjs
node /path/to/pptx_live_preview/live-preview.mjs \
  --pptx "$PWD/out/deck.pptx" --render-dir "$PWD/out/rendered" \
  --watch "$PWD/deck.mjs" --watch "$PWD/theme.mjs" --watch "$PWD/overrides.json" --watch "$PWD/out/deck.pptx" \
  --build-command "node $PWD/tools/build.mjs" --settle 1000
```

Then open `out/deck.pptx` itself in PowerPoint (not a copy), edit, save. The viewer rebuilds, `sync-back`
patches `deck.mjs` / `overrides.json`, and the slides re-render from the saved file.

Requirements in the deck project: `pptxgenjs` installed (`npm install`), LibreOffice and `pdftoppm`
(poppler) for rendering, and a `deck.mjs` / `theme.mjs` that follow the contract below.

## What `build.mjs` does

| Situation (since the last build) | Action |
|---|---|
| only `out/deck.pptx` changed | PowerPoint save → backup → `sync-back` → manifest refreshed from code → render from the saved file |
| only code changed (`deck.mjs`, `theme.mjs`, `overrides.json`, `assets/`) | backup → `node deck.mjs` → render |
| `.pptx` **and** code changed together (a sync, `git checkout`, a cloud push), or the viewer reports both in `PPTX_PREVIEW_CHANGED` | external update → **no sync-back** → manifest from code → render from the `.pptx` |
| `--force` while the `.pptx` holds an unsynced save | sync-back first, then rebuild — a PowerPoint edit is never discarded |
| PowerPoint saves a copy it opened **before** a code rebuild (it does not reload the file) | sync-back diffs against the manifest of the build that copy came from (the closest one among the current manifest and `out/backup/*/manifest.json`), so only your edits are applied and the code changes are kept; then the merged code is regenerated. Close and reopen the `.pptx` to see it |
| `--no-sync` | render only, never patch code |

Every run that overwrites something first copies `out/deck.pptx`, `out/manifest.json`, `deck.mjs`,
`theme.mjs` and `overrides.json` to `out/backup/<timestamp>-<why>/` (last 20 kept). To recover an edit:
`node tools/sync-back.mjs --pptx out/backup/<stamp>-sync/deck.pptx --manifest out/backup/<stamp>-sync/manifest.json --dry-run`.

## What `sync-back.mjs` does

Every shape the build creates carries a stable name `"<slide id>|<kind>|<n>"` and is recorded in
`out/manifest.json` with its text, per-paragraph style and geometry. `sync-back` opens the saved `.pptx`,
finds those shapes, and for each difference:

- text changed, same paragraphs → patches the matching string literal(s) in `deck.mjs`
- paragraphs added / removed → rewrites the array literal (bullets, card bodies, code lines); if it cannot
  be located, stores a text override
- font size / color / bold / italic / alignment → `overrides.json` `fmt` (per paragraph)
- shape fill / border → `overrides.json` `fill` / `line`
- moved / resized → `overrides.json` `{x,y,w,h}`
- deleted → `overrides.json` `{hidden:true}`; a whole slide deleted → `overrides.json` `"slide|<id>": {hidden:true}`
  (the build skips the slide, its block stays in `deck.mjs`; remove the entry to bring it back)
- table cells / rows / column widths → cell text patched when the grid is unchanged, else `cells` / `colW`
- notes changed → patches the `notes:` literal

Shapes added in PowerPoint and slide reordering are reported but cannot flow back. If the file does not look like a save of the manifest's build
(more than 30 % of the shapes missing or foreign), nothing is written: pass `--manifest` for the build you
edited (a backup has it) or `--force`.

Options: `--dry-run`, `--pptx FILE`, `--manifest FILE` (skip the automatic choice of the base build), `--force`.
It writes `out/.sync-base.json` (`{base, current}`) so `build.mjs` knows whether to render the saved file or regenerate.

## Contract for `deck.mjs` / `theme.mjs`

- `node deck.mjs` writes `out/deck.pptx` and `out/manifest.json`; with `DECK_MANIFEST_ONLY=1` it writes
  only the manifest (used after a sync-back so the next save diffs against the patched code).
- Every slide has a unique `id`; every shape is named `"<id>|<kind>|<n>"` (`objectName` in pptxgenjs).
- `manifest.json` = `{ slides: [{id, index, notes}], shapes: { name: {slide, kind, x, y, w, h, paras:[{text, level, bold, italic, size, color, align}], fill, line, cells, colW, file} }, theme?: {colors:{dk1,lt1,…}} }`.
  Recording `theme` lets `sync-back` resolve PowerPoint scheme colors without importing `theme.mjs`.
- `overrides.json` is read by the build: `{ "<name>": { x,y,w,h, hidden, text:[…], fmt:[…], fill, line, cells, colW },
  "slide|<id>": { hidden } }`. A hidden slide is still listed in `manifest.slides` with `hidden: true` and no shapes;
  the slide constructor returns a no-op slide object so the deck code runs unchanged.
- `apply_theme.cjs` writes the deck's colors into `ppt/theme/theme1.xml` after `pres.writeFile` (pptxgenjs
  hard-codes Office's palette); `notes_paragraphs.cjs` turns `\n` in speaker notes into paragraphs.
- `render.sh DECK.pptx OUTDIR` renders `slide-N.png` with LibreOffice + `pdftoppm`.

A reference implementation of `theme.mjs` (UF theme: layouts, `card`, `node`, `table`, `stat`, `figure`,
…) lives in the deck projects that use this; it is deck-specific and not part of this repository.
